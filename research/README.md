# 리서치 백테스트 하네스

`daytrader/`(실전 자동매매 봇)의 매매기법·세팅값이 적절한지, 장 세션(시간대)별로 기법이나
설정값을 다르게 가져가야 하는지를 과거 1분봉으로 검증하는 도구다. **실전 엔진의 코드를
그대로 재사용한다** - 새로 매매 로직을 베껴 쓰지 않는다(아래 "어떻게 검증하는가" 참고).

⚠️ **한 달치 데이터는 "한 가지 장세"의 표본일 뿐이다.** 여기서 나오는 결론은 전부 가설이다 -
실거래(모의매매 포함)에 반영하기 전에 반드시 종이매매(모의)로 다시 확인하라.

## 빠르게 확인하기(네트워크 없이)

```bash
python -m research.run --source synthetic --days 20 --out research/out/
```

합성 시세(daytrader/simulator.py 의 테마 시나리오)로 하네스가 정상 동작하는지만 확인한다.
**성적 자체는 아무 의미가 없다** - 가짜 시세이기 때문이다. 코드가 도는지, 표가 나오는지
확인하는 용도.

## 실제 시세로 돌리기

### 방법 1 - Yahoo Finance (네트워크가 열린 세션에서)

```bash
python -m research.run --source yahoo --days 30 --out research/out/
```

- 코스피(.KS)를 먼저 시도하고 비어 있으면 코스닥(.KQ)으로 넘어간다.
- 받은 봉은 `research/cache/<종목코드>.csv` 에 캐시된다(다음 실행 때 조회 실패해도 캐시로 대신함).
- **이 샌드박스(에이전트 환경)에서는 기본적으로 query1/query2.finance.yahoo.com 접근이
  막혀 있을 수 있다.** 그 경우 명확한 오류 메시지와 함께 실패하고(캐시가 있으면 캐시로
  대체), 네트워크가 열린 로컬 세션에서 다시 실행하면 된다.
- 실측상 야후 1분봉은 **09:00~15:00 까지만** 오고 15:00~15:30(동시호가 포함) 구간이 빠질 수
  있다 - 이 구간에서는 장 막판 강제청산·close_squeeze 기법의 타이밍을 정확히 재현하지 못한다.
- 1분봉 보존 기간에도 한계가 있다(실측상 대략 한 달 안쪽) - `--days` 를 늘려도 그보다 오래된
  구간은 조용히 빠진다(에러가 아니라 "그 구간만 못 받음"으로 처리된다).

### 방법 2 - Toss Open API 키가 있는 로컬 세션

```bash
python -m research.run --source toss --days 30 --out research/out/
```

- `config.yaml` 의 `client_id`/`client_secret` 을 채우거나 환경변수
  `TOSS_CLIENT_ID`/`TOSS_CLIENT_SECRET` 을 설정해야 한다.
- `daytrader/tossapi.py` 의 `TossClient.candles()` 를 그대로 쓴다 - 한 번에 최대 200개까지만
  주므로(라우터·클라이언트 공통 한도, `daytrader/technique_backtest.py` 의 `_ROUTER_BATCH`
  주석 참고) `before` 파라미터로 과거 방향으로 페이지를 넘긴다.
- 이 개발 샌드박스는 네트워크 정책상 Toss API 자체가 막혀 있어 여기서는 항상 실패한다 -
  Toss 키가 있는 사용자의 로컬 세션에서만 쓸 수 있다.

### 방법 3 - 미리 받아 둔 CSV

```bash
python -m research.run --source csv --csv-path my_bars.csv --out research/out/
```

CSV 컬럼: `symbol, ts, open, high, low, close, volume`. `ts` 는 KST 타임존을 포함한 ISO
문자열(`2026-08-01T09:01:00+09:00`)이어야 한다. 정규장(09:00~15:30) 밖의 행은 버려진다.

## 예상 실행 시간

- `--source synthetic --skip-grid`: 종목 10개·20영업일 기준 수 초.
- 가설 그리드까지 포함(기본, `--skip-grid` 없이): 유니버스·기간에 비례해 늘어난다.
  themes.yaml 전체(약 60종목) × 약 20영업일 × 가설 30여 개(변형 포함)를 전부 돌리면
  수십 분 단위가 될 수 있다 - 먼저 `--symbols` 로 종목을 줄이거나 `--skip-grid` 로
  기준선만 빠르게 본 뒤, 필요한 가설만 골라 돌리는 것을 권한다.

## 어떻게 검증하는가(중요)

`research/backtest.py` 는 `daytrader/playbook.py` 의 **실제 진입·청산 로직**
(`Playbook.evaluate_entry`/`evaluate_exit`, 기법 클래스 10여 종)을 그대로 부른다. 새로
매매 판정을 베껴 쓰지 않는다 - `daytrader/engine.py` 의 `try_entries()`/`manage_positions()`
가 만드는 것과 같은 필드를 가진 `ctx`(SimpleNamespace)를 만들어 넘길 뿐이다:

- 봉은 **닫힌 봉만** 쓴다(진행 중인 봉으로 판단하지 않음 - `entry.use_closed_bars_only` 와
  같은 원칙).
- `session_vwap`/`session_high` 는 그 날 09:00 부터 실제로 누적한 값이다(엔진의
  `_session_stats_for()` 와 같은 계산식) - 받아 온 봉 창만으로 근사하지 않는다.
- 전일 고가·저가(`volatility_breakout` 기법용)도 실제 전일 값을 쓴다.

종목 선정(스크리너 게이팅, `[7-2]`):

- **`screener_gate=True`(기본)** - 로드한 유니버스 전체를 매 틱 평가하지 않는다. 실전의
  `daytrader/screener.py`(`Screener.build_report()`)와 같은 규칙(등락률 3~12% 동반상승 2종목
  이상인 테마만, 상위 `top_themes`개 테마에서 테마당 `candidates_per_theme`종목까지, 가격대·
  거래대금(`min_trading_amount`) 하한)을 `research/backtest.py`의 `_score_themes_approx`/
  `_pick_candidates_approx`가 캐시된 분봉만으로 근사해, `cfg.entry.rescreen_minutes`마다 후보를
  다시 뽑는다(등락률은 그날 시가 대비, 거래대금은 그날 09:00부터 누적한 (전형가×거래량)의 합으로
  근사 - 실시간 랭킹 API가 없어 뉴스·유의종목·ETF/우선주 필터는 뺀다). **이 게이팅이 없으면
  "실전과 다른(훨씬 큰) 유니버스를 매매하는 전략"을 채점하는 셈이라 거래 수가 부풀고 품질 낮은
  진입이 섞여 승률·기대값이 실전보다 체계적으로 나쁘게 나온다** - 실측으로 확인한 하네스 편향이다.
- `screener_gate=False`로 끄면 예전처럼 유니버스 전체를 그대로 평가한다(게이팅 자체의 영향을
  따로 보고 싶을 때만 쓴다).

체결·비용:

- 진입: 신호가 확정된 **닫힌 봉의 다음 봉 시가**에, 슬리피지(기본
  `risk.max_slippage_pct/2` + 1틱)를 얹어 체결한다. 그 날 마지막 봉에서 난 신호는
  체결할 다음 봉이 없어 버려진다.
- 청산: 매 봉의 저가/고가로 봉 안에서 손절·익절이 닿았는지 본다. **둘 다 닿았으면 손절이
  먼저 났다고 본다**(보수적 가정).
- 비용은 `daytrader/ticks.py` 의 `trade_pnl()`(매수·매도 수수료 + 매도세)을 그대로 쓴다 -
  실전 엔진과 다른 손익 계산식을 쓰면 두 성적을 비교할 수 없기 때문이다.
- `max_positions`·`daily_max_trades`·재진입 쿨다운(`cooldown_minutes`)을 지킨다.

**재현하지 않은 것**(정직하게 밝힌다, `research/backtest.py` 모듈 독스트링에도 같은 내용이
있다):

- 분할 매수(피라미딩)·분할 매도의 실제 수량 나눔(단, `scale_out=True` 로 실험하면 고정
  익절이 꺼지는 실제 부작용은 재현된다 - `playbook.FixedExit` 코드 그대로).
  **★★★ 중요 - `config.yaml` 의 기본값이 `sizing.scale_out: true` 이므로, 아무 옵션도
  안 주는 "기준선(baseline)" 결과는 이미 이 상태로 돈다.** 실전은 `scale_out=true` 일 때
  이익이 나는 종목을 1차(목표폭의 절반)·2차(목표폭)에서 나눠 팔아 수익을 중간중간
  챙기지만(`sizing.exit_step`), 이 하네스는 "나눠 판다" 자체를 흉내내지 않고 고정
  전량 익절(`FixedExit`)만 끄기 때문에, 기준선의 모든 거래는 사실상 "익절 없이 손절·
  ATR손절·추적손절·시간손절·모멘텀소멸·강제청산으로만 끝난다" - 실측으로도 기준선
  거래 중 `fixed` 청산(손절이든 익절이든)은 0건이었다. **즉 기준선의 승률·기대값은
  실전보다 체계적으로 더 나쁘게 나온다(이익을 중간에 챙기는 실전 대비 훨씬 가혹한
  대용치다)** - 승률 숫자 자체를 "이 전략은 나쁘다"는 근거로 곧이곧대로 읽으면 안 된다.
  2절의 `c_trailing_and_scaleout` 가설이 `scale_out=False`(고정 익절 8% 그대로) 대안을
  같이 보여주니 참고하라 - 이것도 실전(부분매도)의 정확한 대용은 아니지만, 최소한
  "끝까지 들고 가면 어떻게 끝났을지"는 보여준다.
- VI(상한가 근접)·호가 잔량·체결 우선순위·뉴스 반응.
- 주간(weekly) 손실 한도. 연속 손절 정지(`max_consecutive_losses`)는 구현했지만
  `reduce_after_loss=True`(기본값)면 실전처럼 "정지"가 아니라 "축소 매수"가 맞는 동작인데,
  축소 매수는 흉내내지 않는다.

## 보고서 읽는 법(`research/out/report.md`)

1. **기준선(1절)** - 지금 `config.yaml` 그대로 돌렸을 때 기법×세션별 성적. 거래수가
   적은 셀(특히 30건 미만)은 승률·기대값이 운일 수 있다 - `기대값 90%CI` 열이 0을 크게
   걸치면 그 셀은 아직 결론을 내리기엔 이르다는 뜻이다.
2. **가설 그리드(2절)** - 앞 70%(in-sample)로 각 가설의 여러 변형 중 "기대값이 가장 높고,
   거래 30건 이상이고, 비슷한 이웃 설정도 있는(과최적화 아닌)" 것을 고른 뒤, 뒤 30%
   (out-of-sample)에서 기준과 비교한다. **"기준 이김(OOS)" 열이 "예"인 것만** 실제로
   의미가 있을 가능성이 있다 - "아니오"는 in-sample 에서만 좋아 보였던(과최적화) 경우다.
3. **추천 세션 프로필(3절)** - 2절에서 OOS 로 검증된 것과, 1절에서 표본이 있는데도 뚜렷하게
   마이너스인 조합을 모아 "다음에 시험해 볼 가설"로 제시한다. **확정된 결론이 아니다.**
4. **한계(4절)** - 표본 크기·한 달=한 장세·다중검정·야후 결측·themes.yaml 생존편향 등.
   반드시 함께 읽어라.

## 실거래 반영 전 체크리스트

1. 이 보고서의 추천이 **out-of-sample 에서도** 기준을 이겼는지 확인한다(2절 표).
2. 거래 수가 최소 30건 이상인 셀만 신뢰한다. 그 미만은 "더 지켜볼 가설"일 뿐이다.
3. 서로 다른 달·서로 다른 장세(상승장·횡보장·급락장)로 다시 돌려 같은 결론이 나오는지
   확인한다. 한 달치 결과 하나로 설정을 바꾸지 마라.
4. 설정을 바꾸기 전에 **모의매매(paper 모드)로 최소 1~2주 확인**한 뒤 실거래에 반영한다.
5. themes.yaml 은 계속 바뀐다 - 오늘의 테마 사전으로 한 달 전을 검증한 결과에는
   생존편향(그때는 없었을 종목이 섞여 있음)이 있다는 것을 기억한다.
